## Follow-up diagnosis (2026-10-14)

- Rechecked both journals against the actual Shizuku sender: SENDER_CLIENT_CONNECTED is recorded only after the initial ACK send returns. This proves the sender processed HELLO and submitted an ACK, not successful delivery to the receiver. Repeated HELLO from the same client IP also receives another ACK; there is no one-shot-only ACK bug in this sender path.
- In the selected incident interval, receiver endings include 16 NO_ACK, 16 ACK_TIMEOUT, 20 transport errors and 2 cancellations. All 16 same-source retries following NO_ACK start after only 38–67 ms, rather than the configured minimum 1 second. This independently confirms the retry scheduling defect.
- The 16 ACK_TIMEOUT sessions lasted about 0.75–4.27 seconds, below both the 6-second no-reply limit and nominal 30-second handshake deadline. The old handshake falls through to ACK_TIMEOUT when stopped/cancelled; those entries cannot be counted as 16 additional genuine network timeouts. The local cancellation-classification correction addresses this misleading evidence.
- Two short sessions did reach audio packet processing (3 and 2 packets). Do not characterize test19 as never receiving any packet, or assume a deterministic wire-version incompatibility. Both reports use security OFF without encryption; this incident does not show key/authentication rejection.
- Background-only ADB checks confirmed both devices remain accessible. Current routes are ordinary router Wi-Fi, not the incident's former network topology; current connectivity cannot establish the historical packet route. No device UI, playback, installation or configuration was changed.
- Remaining evidence gap: the exported historical journals do not record the actual chosen receiving network/socket endpoint and reply source. Therefore route selection, kernel connected-socket filtering and actual return-path loss remain distinguishable hypotheses, not proven causes. Communication sharing itself is not diagnosed as faulty. A controlled comparison must retain source authentication/isolation and capture endpoint/route evidence before changing filtering.

## Consolidated proposal requested by user (2026-10-14)

This checkpoint records a plan; it does not authorize new device interaction or claim the remaining implementation is complete. Retain the current branch and scoped commits in Draft PR #40. Product edits already present remain uncommitted; this planning turn changes documentation only.

1. **Reception and recovery (#37/#39).** Complete the known retry-delay and cancellation-classification repairs. Compare destination-bound versus system-routed sockets in a controlled test, with bounded endpoint/route and rejected-packet evidence. Repair only the demonstrated boundary; do not accept arbitrary source addresses. Preserve independent sources, authentication and WFAS v2. Acceptance covers both directions with test16, ordinary Wi-Fi and the user's communication-sharing network.
2. **Selectable sender playback (#41).** Persist an explicit local-playback or remote-only choice. In local-playback mode, hardware keys adjust the sender's local system playback; transmission gain remains separately adjustable. In remote-only mode, suppress local rendering through the capture route and expose transmission gain to hardware volume controls through an appropriate media session/volume provider. Activity key interception alone is insufficient. Preserve existing behavior on upgrade; a mode change requiring capture recreation must report its result and restore routing on failure/stop. Test foreground, another app, lock screen and explicit stop.
3. **Volume scale and memory (#42).** Transmission display is 0–100%, with 50%=unity and 100%=the old gain-2 ceiling. Use one conversion in UI, notifications, overlays, hardware controls and remote controls. Save on changes in order, not only at normal session end; retain values across disconnect/recreation. Default 50% only without saved transmission state. Memory and scale are locally implemented, not yet real-device accepted. Amplification beyond unity can clip PCM; add bounded peak protection and clipping/limiter evidence with a focused implementation and tests, rather than claim the scale change preserves lossless audio at all gains.
4. **Actual remote sender control (#43).** Separate receiver-local master gain, per-source mix gain/mute and each sender's transmission volume. Negotiate optional control support; query authoritative sender volume on connect/reconnect. Receiver changes carry identifiers/order and become confirmed only on sender acknowledgement. Sender-side changes update subscribed receivers. Keep each source isolated; retry controls within bounds, show pending/failed state, and authenticate/replay-protect controls in authenticated sessions. Old senders keep streaming audio and explicitly show remote-control unsupported; a local gain slider must not pretend to change them.
5. **Long-duration sound (#5/#14/#38).** Preserve existing queue bounds and partial-write tails. Correlate capture non-read versus silent PCM, clipping, source packet loss/reordering, discarded FIFO audio, output underruns/rate and recoveries. Confirmed implementation edges: the nominal 5ms fade currently ends after one short chunk; internal governor flushes do not explicitly request a new fade. Propose a small cross-chunk fade state with once-only scaling across partial/zero writes and recovery notifications. These are continuity risks, not established causes of the user's overnight noise. Adjust clock-drift correction only if evidence shows it is excessive. Receiver retains adaptive or continuous integer-ms manual target selection and current user values; sender packet payload and receiver playback target remain different controls. Buffer target is not total measured end-to-end latency.
6. **Background intent and network changes (#39 and focused follow-up before implementation).** Code review confirms service destruction can call handleStoppedWithTask and persist OFF solely because appTasks is empty. This is insufficient evidence of explicit user stop. Clear running intent on actual stop/task-removal; preserve it on ordinary system service destruction and use existing recovery ownership. Whether this caused the reported incident remains unconfirmed. Handle Wi-Fi loss as waiting/offline, retire stale attempts and reconnect on valid routes. A temporarily lost sender should not stop other mixed sources. OEM force-stop cannot be repaired by promising in-process automatic restart; preserve exit evidence and explain it after next launch. Do not modify battery/VPN preferences automatically.
7. **Actionable diagnostics and notification behavior (#32/#38).** Keep bounded/redacted private journals, add source/session/attempt correlation, both handshake directions, selected endpoints/routes and explicit lifecycle reasons. Split zero-byte reads from genuine silent PCM and include output/clip counters. For future background retrieval, implement only a narrowly authorized shell-access export path, app-private by default, with a focused work item before code; never make private logs globally readable. Retain the consolidated single runtime notification per device role, with useful status/mode/volume controls; OEM visual grouping alone does not establish runtime failure.
8. **Delivery and acceptance.** Deliver a CI-signed independent test20 prerelease in io.github.mu23xr.audiobridge.test using the test16 permanent identity. It upgrades the test19 preview only; stable io.github.mu23xr.audiobridge and its data remain intact. Use focused commits for networking, playback intent/mode, volume controls and audio/diagnostics; Android/Windows/governance checks must pass. Arrange device acceptance only after the build is concrete and the user permits the window. Long listening evidence comes from normal use; do not demand immediate reproduction of intermittent noise. Keep test16 as rollback, no new stable promotion or issue closure until acceptance.
