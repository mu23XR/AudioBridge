## Established code facts

- The receiver has used a common multi-source-capable controller since test19. Each source owns its socket and AudioTrack. ReceiverMixer only ramps gains; it adds no PCM queue, cross-source synchronization barrier or source-count-dependent latency target. A single full-weight source is multiplied by receiver master gain, without normalization loss. Remembered sources can independently reconnect; actual active count is unknown in this incident.
- ReceiverPlayout has a software FIFO with 60ms capacity; that is a bound, not a mandatory wait. Each loop calls PcmQueue.drain once, which handles one chunk, then delay(2). At48kHz/stereo/PCM16, a supported256B payload contains1.333ms, requiring750 chunks/sec. A consumer delayed2ms per chunk cannot sustain that rate even without other work. Larger packets such as450/612B are not proven to fail, but background scheduling and partial writes reduce headroom. This defect affects a single source and was introduced in test19, unchanged in20.
- The pre-write gate and PlayoutGovernor retune observe native AudioTrack buffering. Software FIFO occupancy is only included in SOURCE_PLAYOUT_STATS totalBufferedMs, not in the governor's feedback. ReceiverPlayout no longer calls governor.shouldDrop or hardResyncIfNeeded; FIFO eviction and output admission now own part of that responsibility. This supports possible extra variable queueing and discard discontinuities, not a measurement of the user's delay. AudioTrack capacity160ms in adaptive mode is likewise not evidence of160ms actual latency.
- test20 adds reusable output-copy/cross-chunk fade handling; it does not change the FIFO capacity, targets or mixer from19. The5ms ramp changes sample amplitude without inserting5ms of silence or lookahead. It restarts on discontinuities/rebuilds/configuration/flush, not every ordinary packet.
- ReceiverTransport omits zero/flagged-silent PCM from playback and resumes with a short fade-in. test16 used a fade-out/concealment transition and subsequent zero PCM. PlaybackHealth can still regard recent PCM as flowing for3s after it stops. Silence-boundary clicks/false starvation adaptation merit investigation, but restoring unconditional zero-PCM feeding could reintroduce OEM output suspension. Neither candidate is established as the incident cause.
- ClientSessionController.Entry.announce becomes false after connected status, including a silent audio packet. connect/restartCurrent/retry reuse the entry without resetting it, so later attempts receive connectionSoundEnabled=false. ReceiverTransport only plays a cue on fresh non-silent PCM. Thus explicit reconnection can lose the cue, and a silent-only first connection emits none. Device preference/route/MediaPlayer failures were not observed; its existing exception handling is silent. Separate this confirmed static behavior from proving why this user heard no cue.
- test20 gain above unity uses nonlinear peak compression; display50%=unity,100%=gain2. Unity bytes are unchanged by the limiter. Without current gain/limited-sample counters, do not attribute stutter/pops to it or claim above-unity output is lossless.

## Detailed repair proposal requested by user

This follow-up is a proposal only. Prior diagnostic documentation edits are retained; product source and devices remain unchanged.

- **Scheduling first.** Wake the existing per-source player when PCM is offered. Drain multiple queued chunks while native output has space, bounding each batch by audio duration/headroom and CPU work. Stop draining on a zero write or cancellation; retain partial tails exactly once. Conflate data wakeups safely; configuration, stop and timed output-progress/health work must also wake the player when input is absent. Suspend when no input exists, and wait briefly for playback progress when output is full. Removing delay(2) alone would create a busy loop and is not the proposed repair.
- **One visible backlog budget.** Track both software FIFO and native queued duration. Use their sum for backlog/latency-budget decisions, while treating device clock drift separately from bursty network arrival. Do not blindly replace the drift controller's occupancy input with a raw FIFO-inclusive sample: network bursts must not create pitch modulation. Evict stale audio only beyond a deliberate bounded budget, smoothing discontinuities and recording the reason/amount; do not simply enlarge buffers. Preserve adaptive/manual selection and stored user values. A target is not an end-to-end latency measurement.
- **Continuity and silence.** Distinguish a sender's intentional silence from missing packets and playback starvation. Pause/resume should not create false adaptive increases. Keep input/output isolation, brief loss concealment and safe silence transitions; validate fade-out/fade-in and avoid repeated flushes. Above-unity gain compression and capture clipping remain separate evidence candidates rather than assumed causes.
- **Connection cues.** Reset eligibility on an explicit user reconnect/new logical connection. Announce a validated successful-session transition after a first valid source frame, including a silent frame, with handshake/authentication complete when applicable; merely receiving a HELLO/ACK is insufficient. Silent content must not suppress the successful-connection cue. Automatic retry cues need deduplication, and player failures need bounded diagnostic evidence. Respect the user's cue preference.
- **Single and multiple sources.** Keep one implementation with independent source queues/clocks, allocating output only for actual sources. One source has no cross-source barrier; adding another must not change the first source's stored latency target. Confirm remembered source count and route from logs when reachable, instead of assuming all stored entries are actively mixing.
- **Acceptance and delivery.** Start with small-payload throughput, jitter, partial/zero-write, silence/resume and explicit reconnect regressions. Compare identical audio/settings against test20 and test16, separating target/native/software queue times, underruns, discards and playback-rate changes. Normal-use long-run listening remains required after deterministic checks. A later test21 proposal would upgrade the same independent preview package with the permanent signer, retaining stable test16; no build/publication/install is performed by this planning request.
