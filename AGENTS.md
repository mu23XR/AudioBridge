# AudioBridge Agent Guide

This file is the entry point for humans and AI agents working on this repository.

## Start here

Before changing code, read in this order:

1. `AGENTS.md`
2. `docs/PROJECT_STATE.md`
3. Read all open GitHub Issues, starting with the active tracking Issue
4. Read linked open/Draft pull requests for those Issues
5. `docs/ARCHITECTURE.md`
6. `docs/RELEASE.md`
7. `docs/SIGNING.md`
8. `WFAS_PROTOCOL.md` when touching networking/protocol behavior

## Non-negotiable rules

- Default branch: `main`.
- Repository: `mu23XR/AudioBridge`.
- Android application id: `io.github.mu23xr.audiobridge`.
- Android release signing identity is fixed. See `docs/SIGNING.md`.
- Never commit keystores, private keys, passwords, tokens, cookies or exported secrets.
- Never generate a replacement Android release key automatically.
- Stable releases must be produced by the root `.github/workflows/release.yml` workflow.
- Test builds and stable builds must use the same permanent Android signing identity.
- A wire-incompatible WFAS change requires a protocol-version bump and coordinated Android/Desktop changes.
- The root `WFAS_PROTOCOL.md` is the only protocol specification source of truth.
- Do not edit production/stable behavior merely to make a test pass; fix the underlying issue.
- Do not merge a change that fails Android, Desktop or governance CI.

## Change discipline

Prefer a short-lived branch and PR for non-trivial work. Keep commits scoped and descriptive.

For Android runtime/service changes, explicitly check:
- start/stop lifecycle
- Home/lock-screen behavior
- Recents swipe/task removal
- Shizuku UserService cleanup
- audio route restoration
- reconnect behavior
- sender/receiver role transitions

For cross-platform protocol changes, validate both Android and Desktop before release.

## Release discipline

Stable releases use semantic tags of the form `vMAJOR.MINOR.PATCH`.
Prerelease/test builds must not silently replace the stable GitHub Release.
Release assets are generated by CI; do not hand-sign random APKs and upload them as stable.

## Documentation discipline

When behavior, release flow, signing, package identity, protocol or known issues change, update the corresponding document in the same PR.


## Issue tracking discipline

GitHub Issues are the source of truth for active bugs and feature work.

- Every reproducible bug gets its own Issue.
- Every active feature gets its own Issue before substantial implementation.
- Keep one Issue focused on one problem.
- Record reproduction steps, environment, expected behavior, actual behavior and acceptance criteria.
- Link the implementation PR from the Issue.
- Do not close an Issue merely because code compiles or CI is green.
- Close a bug only after its acceptance/regression test passes.
- When user testing disproves a fix, update the existing Issue instead of creating a duplicate.
- `docs/PROJECT_STATE.md` summarizes project state; it does not replace the Issue tracker.
- Chat history is supporting context only and must not be the sole record of an active bug.
